1. Executive summary

During a disaster, the region that most needs to record reports is often the one that has lost its connection to everyone else. Most cloud databases force a bad choice: refuse writes until the network returns, or accept writes and silently overwrite whichever edit has the older timestamp.

We are building a replicated report service that takes a third path:

  • Always accept a report locally, instantly, even when cut off.
  • Never silently lose a write. Conflicts are kept in a visible ledger and resolved by clear rules or a human operator.
  • Tell the truth about safety: every report is marked local, replicated or confirmed.
  • Prove history is intact. Every event is hash-chained, so editing, deleting or forging a stored event is detectable, and a replica rejects forged events from a bad peer.
  • Prove it with numbers. In 100 fault-injection trials per system, last-writer-wins silently lost 42.2% of acknowledged edits; our engine lost 0%.
  • Stay provider-independent. No managed database service is used, so the same nodes can run on AWS and Google Cloud and survive a whole-provider failure.
One-sentence pitch. Cloud providers move data between regions; we make that replication trustworthy and understandable during a disaster, by keeping every write, exposing every conflict, and showing what is still at risk.

Where we are today

The replication engine is built and verified: three nodes replicate, survive partitions, crashes and wrong clocks, and converge to identical state. It runs in Docker and is deployed as three servers on AWS (Mumbai, Hyderabad, Singapore), where the full partition, heal and crash-recovery scenario passes 12 of 12 checks. The comparison benchmark against a last-writer-wins baseline is complete (section 9). The operator dashboard and a run of the mixed AWS and Google Cloud deployment are the remaining work.

3. How it works

3.1 Inside one node

HTTP APIcreate, edit, read
→
Event logappend-only SQLite
→
Merge engineevents → report
→
Conflict ledgernothing dropped
→
Statusdurability, hash
  • Events, not rows. Every create or edit is stored as an immutable event. A report's current state is calculated from its events. Nothing is edited or deleted, so nothing can be silently overwritten.
  • Hybrid logical clocks. Each event carries a clock value that never goes backwards and is advanced by events received from other nodes, so a node with a wrong wall clock cannot corrupt ordering.
  • Version vectors. Each event records what its author had already seen. This tells "one edit after another" apart from "two edits at the same time", which timestamps alone cannot do.
  • Pure merge function. The merged result depends only on the set of events, not the order they arrived in, so any two nodes holding the same events compute the same state.

3.2 Replication

Ask"here is what I have"
→
Receiveonly what is missing
→
Apply in orderper origin, no gaps
→
Recordwhat the peer holds
  • Each node pulls from every peer every 0.5 s. A dead peer never delays the others (one thread per peer).
  • Applying an event twice does nothing; events arriving out of order or with gaps are skipped and refetched.
  • Nodes relay for each other: if Mumbai cannot reach Hyderabad but both reach Singapore, they still converge.
  • Long outages catch up in batches of 500 events, always a gap-free prefix.
  • Reset epochs stop a freshly wiped node from receiving old data back from a peer not yet wiped.

3.3 Merge rules (the consistency policy)

FieldTwo edits at the same timeWhy this rule
Severity (1-5)Highest value wins; lowering needs an operatorIn a disaster, under-reporting is more dangerous than over-reporting
StatusMost advanced wins (open < acknowledged < in progress < resolved); reopening needs an operatorWork already done should not be silently undone by a stale update
LocationLatest wins; if the two are more than 500 m apart, flag for an operatorSmall corrections are safe; large jumps need a human
DescriptionKeep both versions and ask an operatorFree text cannot be merged safely by a rule
Type, reporterFixed at creationIdentity of a report must not drift

If a later edit was written by someone who had already seen both versions, it simply supersedes them. Every concurrent disagreement stays in the ledger as history, whether a rule or a person resolved it.

3.4 Durability: telling the truth about risk

StatusMeaning
localOnly this node holds the report. If this node is lost, the report is lost.
replicatedAt least one other node is known to hold every event of the report.
confirmedEvery other node is known to hold it.

3.5 Verification built into the system

Each node exposes a hash of its merged state and the list of event ids it holds. Equal hashes mean two nodes hold the same events and merged them identically. An automated tester uses these to check, after every fault run, that nothing was lost and everything converged.

4. Consistency model and why we chose it

Our choice: available, eventually consistent

  • Every node always accepts writes (availability under partition).
  • All nodes converge to the same state once they exchange events (strong eventual consistency).
  • No acknowledged write is ever discarded; disagreements are surfaced, not hidden.

Why not strong consistency?

  • A strongly consistent system must refuse writes on the side without a majority.
  • In a disaster that is exactly the side that needs to keep recording reports.
  • Reports are mostly new facts that accumulate, so merging is practical and safe.
The honest limit. A report saved in a region that is destroyed before it syncs is lost. No design removes this. We shrink the window to about half a second and show operators which reports are still local, so the risk is visible instead of hidden.

5. Existing approaches and where they fall short

Evidence level: verified means confirmed in documentation or papers during our research; general knowledge means widely known but not re-verified by us.

ApproachWhat it doesWhere it falls short for this problemEvidence
DynamoDB Global Tables, eventual mode An isolated region keeps accepting writes and catches up when healthy Conflicts resolved by last writer wins, so one edit is silently discarded; depends on clocks verified
DynamoDB Global Tables, strong mode A write is confirmed only after another region has it Exactly 3 regions (or 2 plus a witness), no transactions, higher write latency; an isolated region cannot get confirmation (our inference) verified (partition behaviour inferred)
AWS Amplify DataStore / AppSync Offline-first client sync with Auto Merge, optimistic concurrency or a custom Lambda Auto Merge prefers the server value for single fields; custom logic is left to the developer; syncs devices to one cloud endpoint; Gen 1 reaches end of life on 1 May 2027 verified
Consensus databases (Spanner, CockroachDB, etcd) Strong consistency through majority agreement The minority side of a partition cannot commit writes general knowledge
Cassandra, Riak, CouchDB Always-writable replicas Typically timestamp-based or revision-based winners that can hide the losing version general knowledge
CRDT libraries (e.g. Automerge) Replicas converge automatically, peer to peer, with no central server Built for collaborative documents; no domain rules (such as severity can only escalate), no operator workflow, no durability status verified (domain gap is our assessment)
Real-world track record (Jepsen) Independent fault-injection testing of databases Found split-brain, lost acknowledged writes and lost updates in production systems, so "it replicates" is not proof verified
Azure Cosmos DB, multi-region writes Always-writable regions with a configurable conflict policy Default is last-writer-wins on a timestamp; conflicts resolved that way do not appear in the conflict feed, and the policy cannot be changed after the container is created verified
AWS QLDB (ledger database) A managed, cryptographically verifiable ledger Retired on 31 July 2025. The suggested replacement, Aurora PostgreSQL with audit logging, is reported to lack the cryptographic verifiability QLDB gave verified (secondary sources)
Cross-cloud replication Distributed SQL such as CockroachDB spans clouds; common practice is active-passive No managed service offers active-active across AWS and Google Cloud that stays writable on the minority side of a partition; consensus systems need a majority search found no counter-example
The gap we target: AWS and others move the data. They do not decide what is true when two regions disagree, do not tell the operator which reports are at risk, and do not ship their own proof that nothing was lost.

6. What is different and innovative

We want to be clear about what is new. Event logs, hybrid clocks and version vectors are established techniques. Our contribution is combining them into a disaster-operations service with behaviour and verification that general-purpose tools do not provide.

IdeaWhat it gives the user
Domain-aware merge rulesSafe defaults for disaster reports: severity escalates, status advances, location jumps are flagged. Not a blanket "latest wins".
Visible conflict ledgerEvery concurrent disagreement is stored with both versions and who decided. Nothing disappears silently.
Per-report durabilityOperators see which individual reports are still at risk, not just a table-level latency number.
Causality, not clocksCorrect behaviour even when a node's clock is an hour wrong. We test this explicitly.
Built-in proofA chaos tester runs random partitions, crashes and clock skew, then asserts convergence and zero lost writes, and compares against a last-writer-wins baseline.
Safe reset across nodesEpoch numbers prevent old data reappearing after a cluster reset, a real operational trap.
Tamper-evident historyEach event is hash-chained to the previous one from the same node. Editing, deleting or forging a stored event is detectable by recomputing the chain, and a replica refuses forged events from a peer, then recovers from an honest one. AWS retired its ledger database, QLDB, in July 2025, so this fills a gap rather than repeating a product.
Independent of any one providerNothing depends on a managed database, so the same image runs on AWS and Google Cloud and a whole-provider outage cannot take all replicas down. Managed services cannot replicate across clouds, and consensus databases cannot write on the minority side of a partition.

12. Questions we expect, and our answers

QuestionAnswer
Why not just use DynamoDB Global Tables?Its default mode resolves conflicts by latest timestamp, so an edit can vanish silently; its strong mode needs another region to confirm each write, which a cut-off region cannot get. We keep accepting writes and keep every version.
What if a region is destroyed?Anything not yet synced is lost. We minimise that window, mark such reports as local, and say so openly.
Why not trust timestamps?Devices in disaster zones often have wrong clocks, so we use causal information from version vectors and logical clocks.
Is this just a CRDT library?No. We use similar convergence ideas but add disaster-specific rules, an operator ledger, durability status and a built-in verification harness.
How do you know it is correct?Per-rule tests, random multi-node fault runs with invariants, and a comparison against a baseline.
Is your baseline fair?It replicates and converges correctly and shares our request validation. It is our own implementation of item-level last-writer-wins, so we describe it as a model of how DynamoDB and Cosmos DB behave by default, not as those products.
What is new compared with a CRDT or AWS?Disaster-specific merge rules with an operator ledger, per-report durability, a tamper-evident hash-chained history that replaces what AWS retired with QLDB, and a design with no managed service, so it runs across cloud providers.
Does it scale?Not tested beyond three nodes and small data. The prototype proves the behaviour, not throughput.
